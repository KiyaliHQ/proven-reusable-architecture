== What is a PRA?

A *Proven Reusable Architecture* is an architectural pattern validated in production, documented and ready to be reused.

[cols="1,1,1,1,1", options="header"]
|===
| Proven | Documented | Reusable | Maintained | AI-Friendly

| Validated in production
| ADR, examples, feedback
| Multi-context, multi-team
| Active governance
| Integrated AI agents
|===

[cols="1,1,1", options="header"]
|===
| ~200 target architects | 7 archetypes | 2 AI agents
|===

== Content Structure

The registry is organized into two scopes. The 7 archetypes are shared across all levels.

[cols="1,4", options="header"]
|===
| Scope | Description

| *Bank-Wide*
| Cross-cutting -- Validated for all domains. 3+ proven-in-use required.

| *Domain-Wide*
| Sector-specific -- Retail Banking, Corporate Banking, Wealth Management, Cards, etc. 1+ proven-in-use.
|===

*7 Archetypes:* Integration . Application . Data . Security . Technology . DevOps . Business

Each PRA contains:

* *Metadata card* -- attributes, status, tags
* *Technical content* -- context, architecture, ADR
* *Experience feedback* -- quantified proven-in-use

Status (`operationalizing`, `operationalized`, `deprecated`) is metadata, not a folder.

== Anatomy of a PRA

Each PRA follows a standardized AsciiDoc (`.adoc`) template with structured metadata.

*Metadata (file header):*

[cols="1,2", options="header"]
|===
| Attribute | Example

| `:pra-archetype:` | `integration`
| `:pra-status:` | `operationalizing`
| `:pra-scope:` | `domain-wide`
| `:pra-origin:` | `retail`
| `:pra-tags:` | `api, gateway, kong`
| `:pra-version:` | `1.0.0`
| `:pra-proven-count:` | `2`
| `:pra-author:` | `A. Tremblay`
| `:pra-created:` | `2025-12-03`
|===

*PRA sections:*

[cols="1,3", options="header"]
|===
| Section | Content

| Metadata card | Auto-generated metadata table
| Summary | 2-3 sentences, why this PRA exists
| Context | When to use / not to use
| Architecture | PlantUML diagrams + tech stack
| ADR | Decisions with compared options
| Implementation | Step-by-step guide with code
| Experience feedback | Quantified proven-in-use
| Limitations | Constraints and known risks
| References | External links
|===

Available templates: `pra-template-fr.adoc` . `pra-template-en.adoc` . `adr-template.adoc`

== Integrated AI Agents

Two AI agents in VS Code, config-driven and structure-agnostic. Zero hardcode.

*PRA Explorer -- Finds and recommends patterns*

* Architect: _"I need to integrate Salesforce in the Corporate domain"_
* Agent: Reads config -> Scans PRAs
* Result: _"Salesforce FSC available -- 2 proven-in-use, satisfaction 8/10"_

*PRA Guide -- Help with processes and governance*

* Architect: _"How do I submit a PRA?"_
* Agent: Reads config -> Consults guides
* Result: _"1. Copy the template -- 2. Document FR + EN -- 3. Submit a PR"_

== Governance and CODEOWNERS

[cols="1,1,1", options="header"]
|===
| Bank-Wide | Domain-Wide | Core Team

| Expert Architects Committee +
5-7 cross-domain experts +
Review: 2-4 weeks +
2 approvals, 3+ proven-in-use
| Domain Committee +
3-5 architects / domain +
Review: 5-10 days +
1+ proven-in-use
| Framework maintenance +
Only team outside `content/pras/` +
CI/CD, scripts, templates +
Features via GitHub Issues
|===

*CODEOWNERS -- Automatic reviewer assignment:*

[cols="2,2,1", options="header"]
|===
| Modified file | Reviewers | Team

| `content/pras/*/bank-wide/` | `@expert-architects-committee` | Bank-Wide
| `content/pras/*/domain-wide/retail/` | `@gov-retail-committee` | Domain-Wide
| `.github/` . `build/` . `scripts/` . `*.yml` | `@pra-core-team` | Core
|===

GitHub automatically assigns reviewers based on the modified file in the PR.

== CI/CD Pipeline

A single merge to `main` updates both platforms automatically.

[plantuml]
----
@startuml
skinparam backgroundColor transparent
skinparam defaultFontSize 12
skinparam shadowing false
skinparam ArrowColor #333333
skinparam sequence {
  ParticipantBackgroundColor #ffffff
  ParticipantBorderColor #d1d5db
}

actor "Architect" as arch
participant "GitHub" as gh #333333
participant "GitHub Actions" as ci #c8102e
participant "GitHub Pages" as ghp #2563eb
participant "Confluence" as conf #2563eb

arch -> gh : Merge PR to main
gh -> ci : Trigger CI/CD

ci -> ghp : Job 1: Asciidoctor\n+ PlantUML -> HTML
ci -> conf : Job 2: Docker\nPublisher -> Pages

ghp --> arch : Site updated (< 2 min)
conf --> arch : Pages updated (< 3 min)

note over ci
  Two parallel jobs
  Zero manual intervention
end note
@enduml
----

*Job 1 -- GitHub Pages:* Asciidoctor + PlantUML -> HTML . Interactive dashboard with filters . Auto-generated sidebar

*Job 2 -- Confluence:* Confluence Publisher (Docker) . Automatic FR / EN hierarchy . Compatible Cloud + Data Center
