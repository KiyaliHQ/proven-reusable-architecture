= Vue d'ensemble architecturale — Registre PRA
:page-title: Vue d'ensemble architecturale
:keywords: architecture, overview, plateforme, ci-cd, gouvernance
:pra-hide-meta: true

Le Registre PRA (Proven Reusable Architecture) est la plateforme centralisee de la Banque Nationale pour cataloguer, partager et gouverner les patrons architecturaux valides en production.

Ce document presente l'architecture complete de la plateforme, ses flux, ses agents IA et sa gouvernance.

== 1. Vue d'ensemble de la plateforme

Le registre suit un modele *Git-centric* : le repository GitHub est la source de verite unique. Deux cibles de publication sont alimentees automatiquement.

[plantuml]
----

skinparam defaultFontSize 13

  rectangle "Agents IA" as agents #fff

  rectangle "Dashboard filtrable" as dash #fff
  rectangle "Fiches PRA" as fiches #fff

  rectangle "Espace PRA" as confSpace #fff
  rectangle "Hierarchie FR/EN" as confTree #fff

actor "Architectes" as arch #6c757d

repo -down-> cicd : merge sur main
cicd -down-> ghpages : Job 1 : Asciidoctor\n+ PlantUML

@enduml
----

*Principe cle* : Git est le seul point d'ecriture. GitHub Pages et Confluence sont des vues en lecture seule, regenerees a chaque merge.

*Point important* : Le statut (`operationalizing`, `operationalized`, `deprecated`) est une metadonnee du PRA, pas un element de la hierarchie de dossiers.

== 4. Agents IA — Architecture

Deux agents IA permettent aux architectes d'interagir avec le registre en langage naturel, directement depuis VS Code ou Claude Code.

[plantuml]
----
@startuml
skinparam backgroundColor transparent
skinparam participant {
  RoundCorner 10
}

actor "Architecte" as arch
participant "PRA Explorer" as explorer #c8102e
database "content/pras/" as pras
database "pra-registry.config.yml" as config

== PRA Explorer : Trouver un pattern ==

arch -> explorer : "Je dois integrer\nSalesforce dans le\ndomaine entreprises"
explorer -> config : Step 0 : Lire config\n(structure, archetypes, domaines)
explorer -> pras : Step 1 : Explorer\ncontent/pras/{lang}/
explorer -> pras : Step 2-3 : Chercher par\ntags, archetyoe, contenu
explorer -> arch : Step 4 : Recommandation\n"Salesforce FSC (Domain-Wide)\n2 proven-in-use, satisfaction 8/10"

@enduml
----

[plantuml]
----
@startuml
skinparam backgroundColor transparent
skinparam participant {
  RoundCorner 10
}

actor "Architecte" as arch
participant "PRA Guide" as guide #1a73e8
database "content/guides/" as guides
database "docs/" as docs
database "pra-registry.config.yml" as config

== PRA Guide : Question process ==

arch -> guide : "Comment soumettre\nun PRA ?"
guide -> config : Step 0 : Lire config
guide -> guides : Step 1 : Explorer\ncontent/guides/{lang}/
guide -> docs : Step 2-3 : Lire\ndocumentation pertinente
guide -> arch : Step 4 : Reponse structuree\n"1. Copier template\n2. Documenter FR+EN\n3. Soumettre PR\n4. Review CODEOWNERS"

@enduml
----

Les deux agents sont *config-driven* (`pra-registry.config.yml`) et *structure-agnostic* : ils decouvrent dynamiquement le contenu sans chemins hardcodes.

== 6. Cycle de vie d'un PRA

Chaque PRA suit un cycle de vie clair, de la contribution initiale jusqu'a la depreciation eventuelle.

[plantuml]
----
@startuml
skinparam backgroundColor transparent
skinparam state {
  RoundCorner 15
  BackgroundColor #fff
  BorderColor #333
}

[*] --> Contribution : Architecte soumet PR

state Contribution #fce4ec {
  state "Branche + Documentation\nFR + EN" as contrib
  state "PR Review\n(CI + CODEOWNERS)" as review
  contrib --> review
}

Contribution --> Operationalizing : Approuve

state Operationalizing #e3f2fd {
  state "1+ proven-in-use" as op1
  state "Collecte retours\nd'experience" as feedback
  op1 --> feedback
}

Operationalizing --> Operationalized : 3+ proven-in-use\n(bank-wide)\nou criteres domaine

state Operationalized #e8f5e9 {
  state "Pattern recommande\npour nouveaux projets" as recommended
  state "Maintenance active\n(< 6 mois depuis MAJ)" as maintained
  recommended --> maintained
}

Operationalized --> Deprecated : Remplace ou obsolete

state Deprecated #ffebee {
  state "Non recommande\npour nouveaux projets" as not_rec
  state "Plan de migration\ndocumente" as migration
  not_rec --> migration
}

Deprecated --> [*]
@enduml
----

== 7. Pipeline CI/CD

A chaque merge sur `main`, deux jobs paralleles publient le contenu en moins de 5 minutes.

[plantuml]
----
@startuml
skinparam backgroundColor transparent
skinparam participant {
  RoundCorner 10
}

actor "Architecte" as arch
participant "GitHub" as gh #333
participant "GitHub Actions" as gha #c8102e
participant "GitHub Pages" as ghp #1a73e8
participant "Confluence Cloud" as conf #1a73e8

arch -> gh : Merge PR sur main
gh -> gha : Declenche workflows\n(push event)

== Job 1 : GitHub Pages (parallele) ==
gha -> gha : Install Java 17\n+ Asciidoctor + PlantUML
gha -> gha : generate-dashboard.sh\n(index/catalogue)
gha -> gha : build.sh\n(.adoc → HTML + PNG)
gha -> ghp : Deploy\n(upload artifact)

== Job 2 : Confluence (parallele) ==
gha -> gha : publish-confluence.sh
gha -> conf : Create/find\nhierarchy pages\n(REST API)
gha -> conf : Sanitize + publish\n14 sous-dossiers\n(Docker Publisher)

ghp -> arch : Site a jour\n(< 2 min)
conf -> arch : Pages a jour\n(< 3 min)
@enduml
----

*Resultat* : Un seul merge sur `main` met a jour les deux plateformes simultanement. Zero intervention manuelle.
