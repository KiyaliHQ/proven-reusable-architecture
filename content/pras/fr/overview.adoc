== Qu'est-ce qu'un PRA ?

Un *Proven Reusable Architecture* est un patron architectural validé en production, documenté et prêt à être réutilisé.

[cols="1,1,1,1,1", options="header"]
|===
| Éprouvé | Documenté | Réutilisable | Maintenu | AI-Friendly

| Validé en production
| ADR, exemples, retours
| Multi-contexte, multi-équipe
| Gouvernance active
| Agents IA intégrés
|===

[cols="1,1,1", options="header"]
|===
| ~200 architectes ciblés | 7 archétypes | 2 agents IA
|===

== Structure du contenu

Le registre est organisé en deux scopes. Les 7 archétypes sont communs à tous les niveaux.

[cols="1,4", options="header"]
|===
| Scope | Description

| *Bank-Wide*
| Transversal — Validé pour tous les domaines. 3+ proven-in-use requis.

| *Domain-Wide*
| Par domaine — Particuliers, Entreprises, Gestion Patrimoine, Carte, etc. 1+ proven-in-use.
|===

*7 Archétypes :* Integration · Application · Data · Security · Technology · DevOps · Business

Chaque PRA contient :

* *Fiche signalétique* — métadonnées, statut, tags
* *Contenu technique* — contexte, architecture, ADR
* *Retours d'expérience* — proven-in-use quantifiés

Le statut (`operationalizing`, `operationalized`, `deprecated`) est une métadonnée, pas un dossier.

== Anatomie d'un PRA

Chaque PRA suit un template standardisé en AsciiDoc (`.adoc`) avec des métadonnées structurées.

*Métadonnées (en-tête du fichier .adoc) :*

[cols="1,2", options="header"]
|===
| Attribut | Exemple

| `:pra-archetype:` | `integration`
| `:pra-status:` | `operationalizing`
| `:pra-scope:` | `domain-wide`
| `:pra-origin:` | `particuliers`
| `:pra-tags:` | `api, gateway, kong`
| `:pra-version:` | `1.0.0`
| `:pra-proven-count:` | `2`
| `:pra-author:` | `A. Tremblay`
| `:pra-created:` | `2025-12-03`
|===

*Sections du PRA :*

[cols="1,3", options="header"]
|===
| Section | Contenu

| Fiche signalétique | Tableau de métadonnées auto-généré
| Résumé | 2-3 phrases, pourquoi ce PRA existe
| Contexte | Quand utiliser / ne pas utiliser
| Architecture | Diagrammes PlantUML + stack technique
| ADR | Décisions avec options comparées
| Implémentation | Guide pas-à-pas avec code
| Retours d'expérience | Proven-in-use quantifiés
| Limitations | Contraintes et risques connus
| Références | Liens externes
|===

Templates disponibles : `pra-template-fr.adoc` · `pra-template-en.adoc` · `adr-template.adoc`

== Agents IA intégrés

Deux agents IA dans VS Code, config-driven et structure-agnostic. Zéro hardcode.

*PRA Explorer — Trouve et recommande des patterns*

* Architecte : _"Je dois intégrer Salesforce dans le domaine Entreprises"_
* Agent : Lit la config → Scanne les PRAs
* Résultat : _"Salesforce FSC disponible — 2 proven-in-use, satisfaction 8/10"_

*PRA Guide — Aide sur les processus et la gouvernance*

* Architecte : _"Comment soumettre un PRA ?"_
* Agent : Lit la config → Consulte les guides
* Résultat : _"1. Copier le template — 2. Documenter FR + EN — 3. Soumettre une PR"_

== Processus de soumission

De la contribution à l'approbation — traçabilité complète dans la Pull Request.

[plantuml]
----
@startuml
skinparam backgroundColor transparent
skinparam defaultFontSize 12
skinparam shadowing false
skinparam roundCorner 10
skinparam ArrowColor #333333

rectangle "Branche +\nDocumentation" as s1 #e3f2fd
rectangle "Pull Request\nCODEOWNERS\nassignés auto" as s2 #e3f2fd
rectangle "Cérémonie\nGouvernance\n(présentation)" as s3 #fff5e1
rectangle "Feedback\n+ Décision" as s4 #fff5e1
rectangle "Approuvé\n→ Merge" as s5 #e8f5e9

s1 -right-> s2
s2 -right-> s3
s3 -right-> s4
s4 -right-> s5
s4 -up-> s2 : Corrections\ndemandées

note bottom of s5
  La PR contient tout l'historique :
  présentations, feedbacks,
  corrections, compte-rendus.
end note
@enduml
----

*Boucle itérative :* Si corrections demandées → commentaires dans la PR → architecte corrige → nouvelle cérémonie → jusqu'à approbation.

== Gouvernance et CODEOWNERS

[cols="1,1,1", options="header"]
|===
| Bank-Wide | Domain-Wide | Équipe Core

| Comité Architectes Experts +
5-7 experts cross-domaines +
Review : 2-4 semaines +
2 approbations, 3+ proven-in-use
| Comité par domaine +
3-5 architectes / domaine +
Review : 5-10 jours +
1+ proven-in-use
| Maintien du framework +
Seule équipe hors `content/pras/` +
CI/CD, scripts, templates +
Features via GitHub Issues
|===

*CODEOWNERS — Assignation automatique des reviewers :*

[cols="2,2,1", options="header"]
|===
| Fichier modifié | Reviewers | Équipe

| `content/pras/*/bank-wide/` | `@comité-architectes-experts` | Bank-Wide
| `content/pras/*/domain-wide/particuliers/` | `@comité-gov-particuliers` | Domain-Wide
| `.github/` · `build/` · `scripts/` · `*.yml` | `@pra-core-team` | Core
|===

GitHub assigne automatiquement les reviewers selon le fichier modifié dans la PR.

== Cycle de vie et promotion

Chaque PRA suit un cycle de vie clair avec possibilité de promotion.

[plantuml]
----

skinparam backgroundColor transparent
skinparam defaultFontSize 13
skinparam shadowing false
skinparam ArrowColor #333333
skinparam state {
  BackgroundColor #ffffff
  BorderColor #d1d5db
}

[*] --> Contribution

state "Contribution" as s1 #fce4ec : PR + Cérémonie\ngouvernance

s1 --> Operationalizing : Approuvé

state "Operationalizing" as s2 #e3f2fd : 1+ proven-in-use\nCollecte de retours

s2 --> Operationalized : Critères atteints\n(3+ bank-wide)

state "Operationalized" as s3 #e8f5e9 : Pattern recommandé\nMaintenance active

s3 --> Deprecated : Remplacé ou obsolète

state "Deprecated" as s4 #ffebee : Non recommandé\nPlan de migration

s4 --> [*]
@enduml
----

*Promotion Domain-Wide → Bank-Wide :* Même processus que la contribution initiale — PRA prouvé dans 3+ projets multi-domaines → PR de promotion → Comité Experts review + cérémonie → Approuvé = Bank-Wide.

== Pipeline CI/CD

Un seul merge sur `main` met à jour les deux plateformes automatiquement.

[plantuml]
----
@startuml
skinparam backgroundColor transparent
skinparam defaultFontSize 12
skinparam shadowing false
skinparam ArrowColor #333333
skinparam sequence {
  ParticipantBackgroundColor #ffffff
  ParticipantBorderColor #d1d5db
}

actor "Architecte" as arch
participant "GitHub" as gh #333333
participant "GitHub Actions" as ci #c8102e
participant "GitHub Pages" as ghp #2563eb
participant "Confluence" as conf #2563eb

arch -> gh : Merge PR sur main
gh -> ci : Déclenche CI/CD

ci -> ghp : Job 1 : Asciidoctor\n+ PlantUML → HTML
ci -> conf : Job 2 : Docker\nPublisher → Pages

ghp --> arch : Site à jour (< 2 min)
conf --> arch : Pages à jour (< 3 min)

note over ci
  Deux jobs parallèles
  Zéro intervention manuelle
end note
@enduml
----

*Job 1 — GitHub Pages :* Asciidoctor + PlantUML → HTML · Dashboard avec filtres interactifs · Sidebar auto-générée

*Job 2 — Confluence :* Confluence Publisher (Docker) · Hiérarchie automatique FR / EN · Compatible Cloud + Data Center
