Overview

L'API Gateway Test Pattern est un pattern d'architecture qui centralise la gestion du trafic API pour les architectures microservices. Il fournit un point d'entrée unique pour les clients, gérant le routage, l'authentification, le rate-limiting et la transformation des requêtes.

Ce pattern a été validé en production dans le contexte des services Particuliers de la Banque Nationale, où il gère actuellement le trafic de 12 microservices avec un SLA de 99.95%.

Contexte

Quand utiliser ce pattern

  • Votre architecture comprend 3 microservices ou plus exposés aux clients
  • Vous avez besoin de rate-limiting centralisé et d'une politique d'authentification unifiée
  • Vous souhaitez découpler la structure interne de vos services de l'API exposée aux consommateurs
  • Vous devez supporter le versioning d'API sans impacter les services en aval

Quand ne PAS utiliser ce pattern

  • Architecture monolithique — un reverse proxy simple (Nginx, Traefik) suffit
  • Communication inter-services uniquement — préférez un service mesh (Istio, Linkerd)
  • Moins de 3 services — la complexité d'un API Gateway n'est pas justifiée

Architecture

Le pattern repose sur Kong Gateway déployé sur Kubernetes, positionné entre le load balancer externe et les microservices internes.

ADR-001 : Choix de Kong vs Envoy

Contexte

L'équipe d'architecture devait choisir une solution d'API Gateway pour la plateforme microservices du domaine Particuliers. Les deux candidats principaux étaient Kong Gateway et Envoy Proxy.

Options considérées

Critère Kong Gateway Envoy Proxy
ConfigurationAdmin API + UIYAML / xDS API
Écosystème plugins100+ plugins prêtsFilters (C++/WASM)
Courbe d'apprentissageModéréeÉlevée
PerformanceTrès bonne (Lua)Excellente (C++)
Support BNC existantOui (licence)Non

Décision

Kong Gateway a été retenu pour les raisons suivantes :

  • Licence entreprise déjà en place à la BNC (réduction du time-to-market)
  • Écosystème de plugins riche couvrant 90% des besoins sans développement custom
  • Admin API déclarative compatible avec nos pipelines GitOps

Conséquences

  • Positif : Mise en production en 3 semaines au lieu de 8 estimées avec Envoy
  • Négatif : Dépendance à la licence commerciale Kong Enterprise
  • Risque mitigé : Kong OSS disponible comme fallback si la licence n'est pas renouvelée

Implémentation

Étape 1 — Déploiement via Helm

Installer Kong Gateway sur votre cluster Kubernetes avec le chart Helm officiel :

# Ajouter le repository Helm Kong helm repo add kong https://charts.konghq.com helm repo update # Installer Kong avec la configuration BNC helm install kong-gateway kong/kong \ --namespace api-gateway \ --set env.database=postgres \ --set env.pg_host=postgres.db.svc.cluster.local \ --set proxy.type=LoadBalancer \ --set admin.enabled=true

Étape 2 — Configuration du routage

Déclarer les services et routes via l'Admin API :

# Créer un service curl -X POST http://localhost:8001/services \ --data name=accounts-service \ --data url=http://accounts.particuliers.svc:8080 # Créer une route curl -X POST http://localhost:8001/services/accounts-service/routes \ --data paths[]=/api/v1/accounts \ --data strip_path=false # Activer le rate-limiting curl -X POST http://localhost:8001/services/accounts-service/plugins \ --data name=rate-limiting \ --data config.minute=100 \ --data config.policy=redis

Retours d'expérience

1
Projet Alpha — Équipe Retail
Déployé en production : 2025-06-15

Résultat : Réduction de 40% de la latence moyenne sur les appels API grâce à la centralisation du caching et du rate-limiting. Le temps de mise en place d'un nouveau microservice exposé via l'API est passé de 2 jours à 2 heures grâce aux templates Kong standardisés.

Limitations

  • Point de défaillance unique (SPOF) : Le gateway doit être déployé en haute disponibilité (minimum 3 réplicas). Un incident sur le gateway impacte tous les services en aval.
  • Latence additionnelle : Chaque requête traverse un hop supplémentaire (~2-5ms en P99). Pour des cas ultra-low-latency, envisager une connexion directe.
  • Complexité opérationnelle : La gestion des plugins, des certificats TLS et du monitoring du gateway nécessite une expertise dédiée au sein de l'équipe plateforme.
